SedaiBasic · demo

A Buddhabrot written in BASIC

The same source compiled to bytecode, to machine code and to WebAssembly. The three of them draw the same picture, byte for byte. The WebAssembly one runs right here, in the browser, with nothing to install.

The interactive page is a single file: it carries the 27 KB WebAssembly module inside it. Tap the picture to zoom in on what you tapped.

What you are looking at

The Mandelbrot picture everyone knows colours each point by how long it takes to escape. This one asks a different question — where do the escaping orbits go on their way out — and answers it by throwing millions of random points at the plane, following the ones that escape, and counting how often each pixel is passed through. The result is a density map. Turned a quarter turn, it looks like a seated figure, which is where the name comes from.

The colour is a third question, not a palette

Each channel counts a different lifetime, and the three thresholds are fractions of the iteration ceiling:

  • Blue — orbits dead within a hundredth of the ceiling. Nine in ten end here: they are barely more than the random point they started from, which is why the haze is blue.
  • Green — the middle lifetimes.
  • Orange — everything that lives longer. The structure is orange because only that channel holds it.

It is not decoration, it is a reading of the data. Press C and the channels swap: the same picture, asked something else.

One source, four ways of running it

SedaiBasic compiles the same file to bytecode and runs it with an interpreter; or compiles the hot loops to machine code while it runs (JIT); or compiles whole functions before it starts (AOT); or emits a WebAssembly module that runs in a browser with no interpreter and no runtime library.

That these really are the same thing is not a claim, it is a check. The four versions trace the same orbits and the files they write have the same SHA-256 hash. It would take one engine rounding differently in one place for an orbit to cross the escape radius a step early, and the pictures would part company.

Computing only, nothing painted. Live, the gap is wider, and the reason is that the frame rate is a budget: an engine that paints quickly has more of it left to compute with. At 400×400 a repaint costs 9 ms interpreted and 1 ms compiled, and in six seconds the interpreter traces 730,000 orbits where the AOT traces 7,400,000 — ten times as much, at exactly the same frames per second.

Building this demo found two defects in the compiler

And that is the most useful part of the story, because neither was visible by reading the code.

The first. PSet — lighting one pixel — had no machine-code lowering in the AOT backend: every pixel went through a runtime helper that flushed and reloaded every allocated register. 60 nanoseconds against the interpreter's 4, so painting was a tax that fell hardest on the fastest engine. It is an inline store now, 1.1 ns.
The second, and the instructive one. With that closed, the AOT still held 43 frames a second where the other two held 58 — and traced fewer orbits than the interpreter. The cause was the opcode next door: RGB() was still a helper call, and a helper call invalidates the descriptor that PSet's fast store hangs on. The two are one pair — PSet (x,y), RGB(r,g,b) is how any graphics program paints — and covering only one of them covered neither. The pixel loop went from 20.5 ms to 0.76 ms a frame.

Why zooming stops converging

A Mandelbrot zoom narrows both what you draw and what you compute. Here it does not: the window narrows but the sampling cannot, because an orbit crossing your window may have started anywhere on the plane. You go on tracing everything and throw away what misses.

The program does exactly the same work at every zoom — slightly faster, in fact, because fewer points land and there is less to write. What collapses is only how much of that work lands where you are looking. It is the problem Metropolis-Hastings sampling exists to solve, and this demo is deliberately uniform: what you are watching is the problem, not the solution.

The source is meant to be read

The whole algorithm is one subroutine and it fits on a screen; everything above it is preparation and everything below it is presentation. The header lists the five things that are easy to get wrong — the orbit that must be buffered before it is accumulated, the two regions that never escape, the mirror symmetry, the iteration floor and the tone curve — and each is called out again at the line where it matters. At the foot of the file is the list of optimisations deliberately not made, with the reason for each.
